# Python runner (AUD-60)

Real Python execution for the Fix stage, run in the **student's own browser** inside an isolated, separately-hosted runner. This document is the deployment guide, threat model, and release checklist. The decision record is [ADR 0003](./decisions/0003-python-runner.md).

> **Status: infrastructure only (PR 1).** There is no student-facing Run button yet (PR 2), and the feature flag is **OFF in production** until every release gate below passes. Nothing here runs student code on StackSpeak's servers, and no student code is ever sent to FastAPI.

## Architecture

```
app  https://stackspeak.vercel.app                       runner  https://<runner>.vercel.app   (a DIFFERENT SITE)
  PythonRunnerClient (frontend/src/lib/pythonRunner)       index.html  ->  bridge.<hash>.mjs      (embeds + owns workers)
     │  hidden <iframe sandbox="allow-scripts allow-same-origin"       │  one Worker PER RUN, terminated afterwards
     │          allow="" referrerpolicy="no-referrer">                 ▼
     │  private MessageChannel (port transferred once)           worker.<hash>.mjs  + self-hosted Pyodide 314.0.7
     └──────────────────────────────────────────────────────────────►  (own CSP header, canary, hardening)
```

| Piece | Where | Role |
|---|---|---|
| Client + session | `frontend/src/lib/pythonRunner/` | creates the iframe, performs the handshake, validates every message, single-flight, watchdogs, fail-closed. **No UI.** |
| Bridge | `runner/src/bridge.mjs` | validates the parent (origin + source + schema, once), owns timeouts/output limits/cleanup, rebuilds every message to the parent from validated fields |
| Worker | `runner/src/worker.mjs` | boots Pyodide (snapshot/cold), proves CSP enforcement, hardens globals, runs one program |
| Harness | `runner/src/harness.py` | fresh namespace per run, main.py-only tracebacks, PRNG reseed |
| Protocol | `runner/src/protocol.mjs` ↔ `frontend/src/lib/pythonRunner/protocol.ts` | shared fixtures prove both validators agree |
| Header rules | `runner/scripts/lib/headers.mjs` | single source for `vercel.json`, the local test server, and the deployment verifier |

### Run lifecycle

1. Nothing downloads until the first Run (connecting loads only the tiny bridge).
2. **First run:** a **builder worker** cold-initialises Pyodide, proves the CSP is enforced, takes a memory snapshot, and is **terminated without ever running student code** — measured: after `makeMemorySnapshot()` that interpreter's JS interop is unreliable (`js.navigator` throws "Illegal invocation"), so it must not run student code.
3. **Every run (including the first):** a **new worker** boots from the snapshot (`restore` mode), runs the program, and is terminated. Every run is a pristine interpreter and every run takes the same path.
4. **Fallbacks (supported, tested):** if the snapshot API is unavailable or a restore fails, the run is retried as a **`cold`** start and the snapshot is marked bad (later runs stay cold); if the CSP canary fails or WebAssembly is missing, Run is **disabled** for the page with a clear reason.
5. Limits (config/runner.config.json): run timeout **5 s**, init timeout **30 s**, output **64 KiB**, code **50,000 chars**, one run at a time. The bridge enforces them; the parent enforces its own watchdogs (init + run + grace; heartbeat loss ⇒ "crashed").

## Exact response headers

Generated by `npm run generate` into the committed `runner/vercel.json` (CI fails on drift). Vercel delivers them; `scripts/verify-deployment.mjs` checks them on the live deployment.

| Path | Header | Value |
|---|---|---|
| `/worker.<hash>.mjs` | `Content-Security-Policy` | `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; worker-src 'none'; base-uri 'none'; form-action 'none'` |
| `/`, `/index.html` | `Content-Security-Policy` | `default-src 'none'; script-src 'self'; worker-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors https://stackspeak.vercel.app` |
| everything | `X-Content-Type-Options` / `Referrer-Policy` / `Permissions-Policy` | `nosniff` / `no-referrer` / camera, microphone, geolocation, USB, serial, … all `()` |
| `/worker.<hash>.mjs`, `/bridge.<hash>.mjs`, `/pyodide/**` | `Cache-Control` | `public, max-age=31536000, immutable` (content-hashed or versioned) |
| `/`, `/index.html`, `/build-info.json` | `Cache-Control` | `public, max-age=0, must-revalidate` |

`connect-src 'self'` is correct **because the runner origin serves only runner files**. Pyodide needs `'wasm-unsafe-eval'` for WebAssembly and does **not** need `'unsafe-eval'`.

## Deployment (Vercel)

The runner is a **separate Vercel project** — never a path or subdomain of the app, and never on a subdomain of the app's registrable domain (that would put it on the same *site*). `*.vercel.app` is on the Public Suffix List, so two `*.vercel.app` projects are different sites.

| Setting | Value |
|---|---|
| Project name | `stackspeak-runner` |
| Git repository / Root Directory | `404Yeti/stackspeak` / `runner` |
| Framework preset | Other |
| Install Command | `npm ci --omit=dev` (devDependencies — Playwright, TypeScript — are not needed to build) |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Ignored Build Step | `git diff HEAD^ HEAD --quiet -- .` (build only when `runner/` changed) |
| Vercel Authentication | **off** — the project serves only public runtime files, and an iframe embedded by the production app cannot authenticate |
| Environment variables | none. Approved origins are **not** read from the environment: a production build ignores every override, so approval can only change through a reviewed edit to `config/runner.config.json` |

**Approving an origin:** edit `approvedParentOrigins` in `runner/config/runner.config.json` (exact `https://` origins; wildcards, paths and duplicates fail the build), run `npm run generate`, commit both files. That list drives `frame-ancestors` **and** the bridge's own parent check. Preview deployments of the app are therefore *not* approved by default: Run is unavailable there (fail closed) until an exact preview origin is added by PR. Production and preview runner deployments of this project share the approved list by design; a fully separate preview runner would be a second project with its own root directory and config, and is deferred.

### Verifying a deployment (required before anything depends on it)

```bash
cd runner
node scripts/verify-deployment.mjs https://<runner-origin>      # exits non-zero on any mismatch; prints raw header evidence
RUNNER_BASE_URL=https://<runner-origin> npm run e2e             # the deployable security/lifecycle subset, in all three browsers
```

The verifier asserts the exact CSP strings, that served worker/bridge bytes hash to the content hash in their filenames, that every Pyodide file matches the committed SHA-256 manifest, caching/nosniff/referrer headers, no cookies, and 404 for unhashed paths. A local server proves nothing about Vercel's edge — this is the check that does.

### Upgrading Pyodide

1. Change the pin in `runner/package.json` **and** `config/runner.config.json` (`pyodideVersion`); `npm install`.
2. `node scripts/build.mjs --update-manifest`, review the new hashes, commit `config/pyodide.sha256.json`.
3. Re-run everything: the snapshot API is private, so a new version can silently change behaviour (cold-start fallback tested via the `forceCold`/`failRestore` hooks).
4. Pyodide is MPL-2.0; it is redistributed unmodified from the npm package.

### Local development

```bash
cd runner
npm ci && npm run build && npm run build:test
npm test                    # node:test — real CPython in Node (harness), config/headers, protocol, build integrity
npm run e2e                 # Playwright: security matrix + lifecycle against the REAL build, 3 browsers
node scripts/serve.mjs --dist dist --port 4010     # serve the production build with the production headers
```
`dist-test/` is a separate tree used only by the tests (hardening off, test hooks on); it is never deployed.

## Failure behaviour

| Situation | Result |
|---|---|
| Parent origin not approved / frame blocked / bridge unreachable | no `hello` ⇒ `unavailable` after the handshake timeout; nothing runs |
| WebAssembly or module workers missing | `fatal: unsupported` — Run disabled for the page |
| Worker CSP not enforced (canary) | `fatal: csp-not-enforced` — Run disabled for the page, **no retry** |
| Runtime file 404 / corrupt / offline | `fatal: init-failed` in seconds (the worker downloads every runtime file itself first — Pyodide alone swallows a failed download and hangs), retryable |
| Download stalls | `fatal: init-timeout` at 30 s, worker terminated |
| Snapshot unavailable or restore fails | supported cold start; snapshot marked bad; run still succeeds |
| Infinite loop | `timeout` at 5 s, worker terminated, next run restores from the snapshot |
| Print flood | `output-limit` within milliseconds (output cap throws in the stdout sink) |
| Runner goes silent (e.g. out of memory) | heartbeat lost ⇒ `crashed`, session failed |

## Threat model

| Threat | Mitigation | Residual |
|---|---|---|
| Infinite loop / CPU | 5 s timeout, `terminate()`, UI thread unaffected | a core is busy ≤ 5 s |
| **Memory exhaustion** | cross-site origin ⇒ own process (Site Isolation), terminate-per-run releases memory, crash detection | **No cap exists.** Measured: 2 GB allocated inside the 5 s window; 3 GB held without `MemoryError`. Can crash the runner process or the student's tab; low-memory phones are the likeliest victims. PR 2 saves the draft before every run and shows a warning (not a block) on low-memory devices |
| Output flood | 64 KiB cap with stop-on-cap, bridge-side cap, parent-side bound | — |
| Exfiltration / LAN probing | worker CSP, canary fail-closed, globals removed | browsers that enforce CSP differently — covered by per-browser CI and the canary |
| App data (cookies, storage, API, page state) | different site; no shared storage/BroadcastChannel (tested); app CORS allow-list excludes the runner | With the worker CSP absent, student code could send a *blind* credentialed request to the app's API. The e2e control shows it carries **no cookie and its response is unreadable** when the app's cookie is `SameSite=Lax`+`HttpOnly`. **Requirement for when auth lands: session cookies must set `SameSite=Lax` (or `Strict`) and `HttpOnly` explicitly** — Firefox does not treat a missing attribute as Lax (observed in this suite), and the canary/CSP, not cookie attributes, is what normally prevents the request at all |
| Persistence / service workers | `worker-src 'none'`; globals removed | — |
| Protocol spoofing | private port, schema validation, bridge rebuilds messages, run ids | student can still print fake-looking text and can lie about *their own* run |
| Hostile embedding / hijack | `frame-ancestors` + bridge origin/source check + exact `targetOrigin` + nonce | approved origin compromise |
| Supply chain | exact pin, lockfile, SHA-256 manifest at build **and** against the deployed files, self-hosted | MPL-2.0; private snapshot API per upgrade |
| Cross-run contamination | fresh interpreter every run | — |
| Student code to our servers | structurally impossible from the runner; asserted in e2e (no non-GET, no marker in any request) | — |

### Guarantees

Student code never runs on StackSpeak servers or in the app's origin; cannot read the app's page, storage, cookies or API responses; cannot send data off-device **where the browser enforces the worker CSP — and Run refuses to start when it cannot prove enforcement**; is terminated at 5 s; starts from a pristine interpreter each run.

### Not guaranteed

Memory limits; that the runner or tab survives a student's own code; identical behaviour on every browser/device (real devices untested); protection from browser vulnerabilities; authenticity of output (a student controls their own output, so it must never be used as grading evidence); correctness of the student's solution (the runner never evaluates it and never reports "passed"/"correct").

## Rollback

Everything is static and stateless: no data, no migrations. Set `NEXT_PUBLIC_PYTHON_RUNNER_ENABLED` to anything but `true` (or remove it) and redeploy the app, or use Vercel *Promote previous deployment* on either project. The backend is untouched.

## Measured performance (local, loopback, test build; not a production figure)

Collected by `runner/e2e/lifecycle.spec.mjs` (`runner/test-results/performance-<browser>.json`), WSL2 dev machine, no network latency.

| Metric | Chromium | Firefox |
|---|---|---|
| Cold start, first ever Run (build snapshot + restore) | 6.2 s | 6.5 s |
| Warm start (restore from cached snapshot), 4 runs | 1.38–1.47 s | 1.32–1.49 s |
| Run duration of the sample program (5 runs) | 198–235 ms | 0–2 ms (**unexplained discrepancy** — likely timer clamping/measurement point differs; to re-measure on a real deployment) |

Other numbers: snapshot ≈30 MB in memory, ≈6.4 MB over the wire for the runtime; `terminate()` released memory (3.3 GB → 0.36 GB in a Node runaway-allocation test); a runaway allocation can reach ≈2 GB in 5 s, so **memory cannot be capped** — only time and output are. WebKit could not be launched locally (missing system libraries; no sudo installs performed), so WebKit/Safari is covered only by the CI `runner` job and the real-device release gate. Deployed-environment numbers are still pending (gate G1).
